# 冷知识星球 - 推荐算法设计

> 版本: v1.2 | 更新日期: 2026-05-19

---

## 一、推荐目标与原则

### 1.1 推荐目标

| 目标 | 说明 | 核心指标 |
|------|------|----------|
| 用户留存 | 让用户每天愿意打开 App | 7 日留存率 |
| 内容消费 | 让用户多浏览知识卡片 | 日均浏览卡片数 |
| 兴趣沉淀 | 让用户找到感兴趣的内容 | 收藏率 |
| 内容发现 | 让优质内容被更多人看到 | 内容覆盖率 |

### 1.2 设计原则

**原则 1: 碎片化友好**
- 用户每次打开 App 只看 3-10 张卡片
- 推荐结果必须"开箱即用"，无需用户思考
- 第一张卡片就要吸引用户

**原则 2: 兴趣探索与利用的平衡**
- 70% 推荐用户已知兴趣类目（利用）
- 30% 推荐用户未接触类目（探索）
- 避免"信息茧房"

**原则 3: 内容新鲜感**
- 同一用户不重复推荐已看过的卡片
- 新发布内容有优先曝光机会
- 定期刷新推荐池

**原则 4: 冷启动友好**
- 新用户首次打开就有优质内容推荐
- 不依赖用户历史行为
- 快速收集用户兴趣信号

## 二、推荐策略设计

### 2.1 策略总览

```
┌─────────────────────────────────────────────────────────────────┐
│                         推荐策略矩阵                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│                    用户状态                                      │
│         ┌──────────────┬──────────────┐                         │
│         │   新用户      │   老用户      │                         │
│    ┌────┼──────────────┼──────────────┤                         │
│    │无行为│  热门推荐    │  热门推荐     │                         │
│ 行 ├────┼──────────────┼──────────────┤                         │
│ 为 │有行为│  兴趣推荐    │  混合推荐     │                         │
│    └────┴──────────────┴──────────────┘                         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**名词解释**:

| 概念 | 定义 | 示例 |
|------|------|------|
| **新用户** | 注册 ≤ 7 天，或浏览卡片数 < 20 | 刚下载 App 的用户 |
| **老用户** | 注册 > 7 天，且浏览卡片数 ≥ 20 | 使用超过一周的活跃用户 |
| **无行为** | 没有产生有效兴趣信号的行为 | 仅快速滑过卡片（浏览 < 3秒）、未收藏、未点击 AI 解读 |
| **有行为** | 产生了有效兴趣信号的行为 | 认真浏览卡片（浏览 ≥ 3秒）、收藏、点击 AI 延伸解读 |

**策略矩阵举例**:

| 场景 | 用户画像 | 推荐策略 | 推荐内容示例 |
|------|----------|----------|-------------|
| 新用户 + 无行为 | 刚注册，快速滑过几张卡片 | 热门推荐 | 全站浏览量 TOP 10 的知识卡片 |
| 新用户 + 有行为 | 刚注册，收藏了 2 张科学类卡片 | 兴趣推荐 | 科学类热门内容 + 其他类目探索内容 |
| 老用户 + 无行为 | 活跃用户，今天只是随便看看 | 热门推荐 | 今日热门 + 新发布内容 |
| 老用户 + 有行为 | 活跃用户，经常浏览历史类内容 | 混合推荐 | 70% 历史类 + 20% 相关类目 + 10% 探索类目 |

### 2.2 策略一：热门推荐

**适用场景**: 新用户、未登录用户、用户主动刷新

**设计思路**:
- 热门 = 大众认可 = 容错率高
- 新用户第一次看到的内容质量有保障
- 避免推荐冷门内容导致用户流失

**热度公式**:
```
热度分 = 浏览量 + 收藏量 × 5 + AI延伸解读量 × 3 + 运营卡片权重 × 10
```

**权重设计理由**:
- 浏览量：基础热度指标
- 收藏量 × 5：收藏是强正向信号，用户认为值得保存
- AI 延伸解读量 × 3：用户主动点击 AI 延伸解读，说明对内容感兴趣
- 运营卡片权重 × 10：运营人员手动调整的权重（-2 到 2），可加权推广或降权惩罚

**时间衰减**:
- 7 天内发布的内容热度分 × 1.5
- 30 天内发布的内容热度分 × 1.0
- 30 天前发布的内容热度分 × 0.8

### 2.3 策略二：兴趣推荐

**适用场景**: 已登录且有行为历史的用户

**设计思路**:
- 基于用户历史行为构建兴趣画像
- 推荐与用户兴趣匹配的内容
- 兴趣会随时间变化，需要动态更新

**兴趣画像构建**:

```
用户兴趣 = Σ (行为权重 × 内容特征)
```

**内容特征说明**:

内容特征是知识卡片的属性标签，用于描述"这条内容是什么"。在本项目中，内容特征主要指：

| 特征维度 | 存储位置 | 示例 |
|---------|----------|------|
| 类目（一级特征） | `t_category` | 日常生活、自然科学、科学原理、数学趣闻、历史故事 |
| 标签（二级特征） | `t_knowledge.tags` | 动物、宇宙、冷门、有趣、量子、恐龙 |
| 资源类型 | `t_knowledge.type` | 图文、视频、音频 |

**公式含义示例**:

假设用户对以下内容有行为：

| 内容 | 类目 | 标签 | 行为 | 行为权重 |
|------|------|------|------|---------|
| 卡片A | 科学 | 量子、物理 | 收藏 | +5 |
| 卡片B | 科学 | 天文、黑洞 | 浏览30秒 | +3 |
| 卡片C | 历史 | 古代、战争 | 浏览10秒 | +2 |

则用户兴趣向量 = 5×(科学+量子+物理) + 3×(科学+天文+黑洞) + 2×(历史+古代+战争)

**一级兴趣（类目）**: 科学=8, 历史=2
**二级兴趣（标签）**: 量子=5, 物理=5, 天文=3, 黑洞=3, 古代=2, 战争=2

结论：该用户对"科学"类目兴趣最高，对"量子"和"物理"标签最感兴趣，应优先推荐科学类量子/物理相关内容。

**行为信号定义**:

| 行为 | 权重 | 说明 |
|------|------|------|
| 浏览（时长 < 3秒） | +0 | 快速滑过，无兴趣信号 |
| 浏览（3-10秒） | +1 | 正常浏览，基础兴趣 |
| 浏览（10-30秒） | +2 | 认真阅读，中等兴趣 |
| 浏览（> 30秒） | +3 | 深度阅读，强兴趣 |
| 收藏 | +5 | 强兴趣信号 |
| 点击 AI 延伸解读 | +2 | 主动探索，中等兴趣 |

**兴趣衰减机制**:
- 每天衰减 5%（乘以 0.95）
- 30 天无互动的兴趣分衰减至原来的 21%
- 避免过时兴趣影响推荐

### 2.4 策略三：混合推荐

**适用场景**: 老用户（有丰富行为历史）

**设计思路**:
- 单一策略都有局限性
- 多策略融合，取长补短
- 动态调整各策略权重

**融合公式**:
```
最终推荐分 = 兴趣分 × 0.4 + 热度分 × 0.3 + 新鲜度分 × 0.2 + 运营权重分 × 0.1
```

**各分项说明**:

| 分项 | 计算方式 | 作用 |
|------|----------|------|
| 兴趣分 | 用户对该类目/标签的兴趣分数 | 个性化匹配 |
| 热度分 | 全局热度排名归一化 | 保证内容质量 |
| 新鲜度分 | 发布时间越近分数越高 | 新内容曝光 |
| 运营权重分 | 卡片权重 × 类目权重 | 运营干预 |

**权重可调整**:
- 运营可根据业务目标调整权重
- A/B 测试找到最优权重组合
- 不同用户群组可使用不同权重

## 三、用户画像设计

### 3.1 两级兴趣体系

```
用户兴趣画像
├── 一级兴趣：类目维度
│   ├── 日常生活
│   ├── 自然科学
│   ├── 科学原理
│   ├── 数学趣闻
│   ├── 历史故事
│   ├── 动物世界
│   ├── 植物王国
│   ├── 人体奥秘
│   ├── 科技前沿
│   └── 文化艺术
│
└── 二级兴趣：标签维度
    ├── 具体标签（如"黑洞"、"恐龙"、"量子"）
    ├── 每个标签独立计分
    └── 标签兴趣可跨类目
```

### 3.2 兴趣分数计算

**一级兴趣（类目）**:
```
类目兴趣分 = Σ (该类目下所有卡片的行为权重) × 运营类目权重
```

**二级兴趣（标签）**:
```
标签兴趣分 = Σ (含该标签的所有卡片的行为权重)
```

**兴趣优先级**:
- 一级兴趣决定大方向（推荐哪个类目）
- 二级兴趣决定精准度（推荐类目下的哪些卡片）
- 二级兴趣可跨类目（如用户喜欢"黑洞"，可能也喜欢物理学相关内容）

### 3.3 兴趣信号采集

**主动信号**:
- 首次登录选择的兴趣类目
- 收藏行为

**被动信号**:
- 浏览行为（看了什么类目/标签）
- 浏览时长（推断兴趣强度）
- AI 延伸解读点击（主动探索信号）

### 3.4 三端参与流程

#### 客户端（采集层）

**职责**: 采集用户行为原始数据，上报至服务端

**信号采集点**:

| 用户操作 | 采集内容 | 上报时机 | 体现位置 | 去重规则 |
|---------|----------|----------|----------|----------|
| 首次登录 | 选择的兴趣类目列表 | 选择完成时 | 注册引导页 | 一次性 |
| 浏览卡片 | 卡片ID、类目、标签、开始时间 | 卡片离开时（滑走/退出） | 首页卡片流、卡片详情页 | 同一用户同一卡片仅计1次 |
| 浏览时长 | 停留秒数 | 卡片离开时 | 首页卡片流、卡片详情页 | 同一用户同一卡片仅计1次 |
| 收藏/取消收藏 | 卡片ID、操作类型 | 操作发生时 | 卡片左下角收藏按钮、卡片详情收藏按钮 | 状态切换，不去重 |
| 点击 AI 延伸解读 | 卡片ID | 点击时 | 卡片底部 AI 解读入口、卡片详情AI延伸解读 | 同一用户同一卡片仅计1次 |
| 上划加载更多 | 加载时间戳 | 加载触发时 | 首页卡片流底部 | 不去重 |
| 类目筛选 | 筛选的类目ID | 筛选时 | 首页顶部类目标签栏 | 不去重 |
| 卡片筛选 | 卡片搜索项 | 搜索时 | 发现页顶部搜索 | 不去重 |

**数据格式**:
```
行为上报 = {
  用户ID,
  卡片ID,
  行为类型（浏览/收藏/AI解读）,
  浏览时长（秒）,
  时间戳
}
```

#### 服务端（计算层）

**职责**: 接收行为数据，更新用户兴趣画像，执行推荐算法

**处理流程**:

```
客户端上报行为
      │
      ▼
┌─────────────────┐
│  行为数据入库    │  → t_behavior_log（行为日志表）
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  计算行为权重    │  → 根据行为类型和浏览时长计算权重分
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  更新兴趣画像    │  → t_user_interest（用户兴趣表）
│  - 一级兴趣(类目)│     累加类目兴趣分
│  - 二级兴趣(标签)│     累加标签兴趣分
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  兴趣分数衰减    │  → 定时任务，每天衰减 5%
└─────────────────┘
```

**存储体现**:

| 数据 | 存储位置 | 说明 |
|------|----------|------|
| 用户行为日志 | `t_behavior_log` | 原始行为记录，用于离线分析 |
| 用户一级兴趣 | `t_user_interest`（type=category） | 类目维度的兴趣分数 |
| 用户二级兴趣 | `t_user_interest`（type=tag） | 标签维度的兴趣分数 |
| 内容热度统计 | `t_knowledge`（view_count, favorite_count） | 卡片维度的热度指标 |

#### 后台运营（干预层）

**职责**: 通过权重配置影响推荐结果，监控推荐效果

**干预方式**:

| 干预手段 | 操作位置 | 影响范围 | 说明 |
|---------|----------|----------|------|
| 卡片权重配置 | 知识管理 → 编辑卡片 | 单张卡片 | 设置 -2 到 2 权重，加权推广或降权惩罚 |
| 类目权重配置 | 类目管理 → 编辑类目 | 整个类目 | 设置 -2 到 2 权重，加权推广或降权惩罚 |
| 内容上下架 | 知识管理 → 上架/下架 | 单张卡片 | 下架内容不再进入推荐池 |
| 推荐效果监控 | Dashboard → 推荐指标 | 全局 | 查看点击率、收藏率、类目分布等指标 |
| 兴趣分布查看 | 用户管理 → 用户画像 | 单个用户 | 查看用户兴趣标签和分数分布 |

**运营看板体现**:

```
推荐效果监控
├── 实时数据
│   ├── 今日推荐次数
│   ├── 点击率 (CTR)
│   ├── 收藏率
│   └── AI延伸解读率
├── 类目分析
│   ├── 各类目推荐占比
│   ├── 各类目点击率对比
│   └── 类目热度趋势
├── 用户分析
│   ├── 兴趣分布（Top 类目/标签）
│   ├── 活跃度分层
│   └── 新老用户占比
└── 内容分析
    ├── 热门卡片 Top 20
    ├── 新内容曝光效果
    └── 低质内容预警
```

## 四、内容画像设计

### 4.1 内容特征

```
内容画像
├── 基础属性
│   ├── 类目归属（一级）
│   ├── 标签列表（二级）
│   └── 资源类型（图文/视频/音频）
├── 质量指标
│   ├── 收藏率 = 收藏数 / 浏览数
│   └── AI延伸解读率 = AI点击数 / 浏览数
├── 热度指标
│   ├── 浏览量
│   ├── 收藏量
│   └── AI延伸解读量
└── 运营指标
    ├── 卡片权重（-2 到 2）
    └── 类目权重（-2 到 2）
```

### 4.2 运营权重机制

**卡片权重（-2 到 2）**:
- -2：强降权，低质/敏感内容
- -1：轻度降权，质量一般内容
- 0：默认权重，无特殊处理
- 1：中等加权，适度增加曝光
- 2：强加权，优先推荐

**类目权重（-2 到 2）**:
- -2：强降权，过季/过剩类目
- -1：轻度降权，暂时减少曝光
- 0：默认权重，无特殊处理
- 1：中等加权，该类目内容适度增加曝光
- 2：强加权，该类目内容优先推荐

**权重应用场景**:
- 节日/活动期间加权相关类目
- 新上线内容加权推广
- 优质内容加权曝光
- 低质内容降权处理

### 4.3 内容质量评估

**质量分 = 收藏率 × 100 + AI延伸解读率 × 50**

**质量等级**:

| 等级 | 质量分范围 | 说明 | 推荐策略 |
|------|-----------|------|----------|
| 优质 | ≥ 15 | 收藏率 ≥ 10% 或 AI解读率 ≥ 20% | 优先推荐 |
| 普通 | 5 - 15 | 有一定互动但不突出 | 正常推荐 |
| 低质 | < 5 | 收藏率 < 3% 且 AI解读率 < 5% | 降权或下架 |

**质量分计算示例**:

| 内容 | 浏览量 | 收藏 | AI解读 | 收藏率 | AI解读率 | 质量分 | 等级 |
|------|--------|------|--------|--------|----------|--------|------|
| 卡片A | 1000 | 150 | 200 | 15% | 20% | 15 + 10 = 25 | 优质 |
| 卡片B | 500 | 30 | 25 | 6% | 5% | 6 + 2.5 = 8.5 | 普通 |
| 卡片C | 200 | 3 | 5 | 1.5% | 2.5% | 1.5 + 1.25 = 2.75 | 低质 |

**说明**:
- 质量分仅反映内容本身的用户反馈质量，与运营权重独立
- 运营权重通过推荐公式中的"运营权重分"单独影响推荐排序
- 新内容（浏览量 < 100）不计算质量分，进入新内容池单独评估

## 五、推荐流程设计

### 5.1 整体流程

```
用户请求推荐
      │
      ▼
┌─────────────────┐
│  判断用户状态    │
└────────┬────────┘
         │
    ┌────┴────────────────┐
    ▼                     ▼
  新用户/无行为          有行为历史
    │                     │
    ▼                     ▼
┌────────────┐     ┌────────────┐
│  热门推荐   │     │  混合推荐   │
└────┬───────┘     └────┬───────┘
     │                  │
     ▼                  ▼
┌────────────────────────────────┐
│         结果后处理              │
│  - 去重（已看过的内容）          │
│  - 多样性控制（类目分布）        │
│  - 运营干预（权重加成）          │
└────────────────────────┬───────┘
                         │
                         ▼
                  返回推荐结果
```

### 5.2 候选集生成

**Step 1: 基础过滤**
- 仅推荐上架状态的内容
- 排除用户已收藏的内容
- 排除用户已浏览过的内容（除非主动刷新）

**Step 2: 类目召回**
- 用户一级兴趣 Top 5 类目 → 召回该类目下内容
- 全局热门类目 → 召回热门内容
- 新发布内容 → 召回新内容

**Step 3: 标签召回**
- 用户二级兴趣 Top 10 标签 → 召回含该标签内容
- 跨类目召回相关内容

**Step 4: 候选集合并**
- 去重
- 候选集大小：200-500 条

### 5.3 排序策略

**粗排**（候选集 → 精选集）:
- 基于简单规则快速筛选
- 保留 50-100 条进入精排

**精排**（精选集 → 推荐列表）:
- 使用融合公式计算最终得分
- 考虑多样性约束
- 应用运营权重
- 生成最终推荐列表

### 5.4 多样性控制

**类目多样性**:
- 连续 3 张卡片不能来自同一类目
- 每 10 张卡片至少覆盖 3 个类目

**内容类型多样性**:
- 图文、视频、音频交替出现
- 避免连续推荐同类型内容

**热度多样性**:
- 热门内容占比 60%
- 中等内容占比 30%
- 冷门内容占比 10%

新用户首次打开 App

## 七、推荐效果评估

### 7.1 核心指标体系

```
推荐效果指标
├── 用户体验指标
│   ├── 点击率 (CTR) = 点击次数 / 推荐次数
│   ├── 收藏率 = 收藏次数 / 点击次数
│   ├── 停留时长 = 平均每张卡片浏览时间
│   ├── 滑动深度 = 平均每次会话浏览卡片数
│   └── AI延伸解读率 = AI点击次数 / 浏览次数
├── 业务价值指标
│   ├── 日活跃用户数 (DAU)
│   ├── 7 日留存率
│   ├── 日均浏览卡片数
│   └── 用户生命周期价值 (LTV)
├── 内容生态指标
│   ├── 内容覆盖率 = 被推荐过的卡片占比
│   ├── 类目均衡度 = 各类目推荐占比的标准差
│   └── 新内容曝光率 = 新内容被推荐的比例
└── 算法效果指标
    ├── 兴趣匹配度 = 兴趣类目内容占比
    ├── 推荐多样性 = 推荐类目分布熵
    └── 推荐新颖度 = 首次推荐内容占比
```

### 7.2 指标目标值

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 点击率 (CTR) | > 15% | 推荐内容吸引力 |
| 收藏率 | > 10% | 内容价值认可 |
| 日均浏览量 | > 10 张 | 用户活跃度 |
| 7 日留存率 | > 40% | 用户粘性 |
| 内容覆盖率 | > 80% | 内容分发均衡 |
| 兴趣匹配度 | > 60% | 个性化程度 |
| AI延伸解读率 | > 20% | 内容深度吸引力 |

## 八、运营干预机制

### 8.1 权重配置

**卡片权重（-2 到 2）**:

| 权重值 | 说明 | 使用场景 |
|--------|------|----------|
| -2 | 强降权 | 低质内容、敏感内容、待下架内容 |
| -1 | 轻度降权 | 质量一般、内容过时 |
| 0 | 默认 | 正常内容 |
| 1 | 中等加权 | 优质内容、活动内容 |
| 2 | 强加权 | 重点推广、节日主题 |

**类目权重（-2 到 2）**:

| 权重值 | 说明 | 使用场景 |
|--------|------|----------|
| -2 | 强降权 | 过季类目、内容过剩类目 |
| -1 | 轻度降权 | 暂时减少曝光的类目 |
| 0 | 默认 | 正常类目 |
| 1 | 中等加权 | 活跃类目、季节性类目 |
| 2 | 强加权 | 重点推广类目 |

### 8.2 系统配置

通过系统配置表（`t_system_config`，group=recommend）可动态调整推荐算法全部参数，无需修改代码。所有配置均带内存缓存（默认 5 分钟 TTL），修改后最多 5 分钟生效。

#### 推荐混合权重（5 个）

| 配置键 | 默认值 | 说明 | 公式位置 |
|--------|--------|------|---------|
| `recommend_content_weight` | 0.4 | 兴趣分权重 | 兴趣分 × 此值 |
| `recommend_hot_weight` | 0.3 | 热度分权重 | 热度分 × 此值 |
| `recommend_new_weight` | 0.2 | 新鲜度分权重 | 新鲜度分 × 此值 |
| `recommend_random_weight` | 0.1 | 随机分权重 | 随机分 × 此值；热门推荐 SQL 随机扰动幅度 |
| `recommend_weight_multiplier` | 10 | 运营权重乘数 | `卡片weight × 此值` 加到最终得分 |

#### 热度分信号权重（3 个）

| 配置键 | 默认值 | 说明 | 公式位置 |
|--------|--------|------|---------|
| `recommend_hot_favorite_weight` | 5 | 收藏量权重 | `favorite_count × 此值` |
| `recommend_hot_ai_extend_weight` | 3 | AI 解读量权重 | `ai_extend_count × 此值` |
| `recommend_hot_weight_multiplier` | 10 | 运营权重乘数 | `weight × 此值` |

同时用于 SQL 热门推荐和 TypeScript `calculateHotScore()`，消除重复硬编码。

#### 时间衰减参数（4 个）

| 配置键 | 默认值 | 说明 | 公式位置 |
|--------|--------|------|---------|
| `recommend_new_content_days` | 7 | 新内容窗口天数 | SQL CASE WHEN + 新鲜度分 |
| `recommend_new_content_boost` | 1.5 | 新内容曝光倍率 | SQL 1.5x + 新鲜度分 |
| `recommend_mid_content_days` | 30 | 中等内容窗口天数 | SQL CASE WHEN + 新鲜度分 |
| `recommend_old_content_penalty` | 0.8 | 老内容衰减系数 | SQL 0.8x + 新鲜度分 |

#### 候选召回参数（4 个）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `recommend_recall_category_interest_limit` | 5 | 一级兴趣（类目）召回数 |
| `recommend_recall_tag_interest_limit` | 10 | 二级兴趣（标签）召回数 |
| `recommend_recall_pool_multiplier` | 5 | 候选池倍率（pageSize × N） |
| `recommend_shuffle_range_multiplier` | 2 | Shuffle 范围倍率（pageSize × N） |

#### 多样性控制（1 个）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `recommend_diversity_consecutive_limit` | 3 | 同类目连续最大张数 |

#### 兴趣衰减参数（2 个）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `recommend_interest_decay_rate` | 0.95 | 每日衰减系数（score × 此值） |
| `recommend_interest_cleanup_threshold` | 0.01 | 兴趣分清理阈值（低于此值删除） |

#### 质量分参数（3 个）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `recommend_quality_min_views` | 100 | 最低浏览量阈值（低于此值不计算质量分） |
| `recommend_quality_favorite_rate_weight` | 100 | 收藏率权重（收藏率 × 此值） |
| `recommend_quality_ai_extend_rate_weight` | 50 | AI 解读率权重（AI 解读率 × 此值） |

#### 行为信号权重（5 个）

| 配置键 | 默认值 | 说明 |
|--------|--------|------|
| `recommend_browse_duration_tiers` | `3,10,30` | 浏览时长分界点（秒），逗号分隔 |
| `recommend_browse_score_tiers` | `1,2,3` | 对应兴趣分值，逗号分隔 |
| `recommend_favorite_score` | 5 | 收藏行为兴趣分值 |

## 九、算法实现

### 9.1 行为信号流转

用户在客户端的每一次交互都会触发行为信号，经过服务端计算后同时影响用户画像和内容画像，最终改变推荐结果。

#### 信号采集与上报

客户端在以下场景采集行为数据，通过 `POST /v1/knowledge/recommend/behavior` 接口上报至服务端：

| 用户交互 | 采集数据 | 上报时机 | 同一用户同一卡片 |
|---------|----------|----------|-----------------|
| 首页卡片流滑动浏览 | 卡片ID + 浏览时长（秒） | 卡片滑走时 | 去重（仅计1次） |
| 详情页浏览 | 卡片ID + 浏览时长（秒） | 页面离开时 | 去重（仅计1次） |
| 收藏卡片 | 卡片ID | 收藏操作时 | 不去重（每次收藏都计） |
| 点击 AI 延伸解读 | 卡片ID | 点击时 | 去重（仅计1次） |

**上报数据格式**:

```
{
  knowledge_id: 卡片ID,
  action: "browse" | "favorite" | "ai_extend",
  browse_duration: 浏览秒数（仅 browse 时有值）
}
```

**上报策略**：Fire-and-forget（发送即忘），不阻塞用户操作，失败静默忽略。

#### 服务端处理流程

服务端收到行为上报后，执行以下处理链：

```
客户端上报行为
      │
      ▼
┌─────────────────────────────┐
│  ① 验证卡片是否存在          │  不存在则忽略
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  ② 去重检查                  │  若 recommend_behavior_dedup_enabled=true
│     查询 recommend_logs      │  同一用户+同一卡片+同一行为类型
│     判断是否已记录过          │  在 recommend_dedup_days 时间窗口内
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  ③ 计算行为权重分            │  根据行为类型和浏览时长
│     browse: <3s→0, 3-10s→1, │
│     10-30s→2, >30s→3        │
│     favorite: +5             │
│     ai_extend: +2            │
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  ④ 写入行为日志              │  → MongoDB recommend_logs
│     记录行为类型、时长等      │
└────────────┬────────────────┘
             │
             ▼
┌─────────────────────────────┐
│  ⑤ 更新用户画像（并行）      │
│     一级兴趣（类目）: 累加分值│  → t_user_interest (type=category)
│     二级兴趣（标签）: 累加分值│  → t_user_interest (type=tag)
└─────────────────────────────┘
```

### 9.2 用户画像计算

用户画像是推荐个性化的基础，由两级兴趣体系构成。

#### 一级兴趣（类目维度）

当用户对某张卡片产生行为时，该卡片所属类目的兴趣分被累加。

**计算规则**：

| 用户行为 | 类目兴趣分变化 | 说明 |
|---------|---------------|------|
| 浏览 < 3 秒 | +0 | 快速滑过，无兴趣信号 |
| 浏览 3-10 秒 | +1 | 基础兴趣 |
| 浏览 10-30 秒 | +2 | 中等兴趣 |
| 浏览 > 30 秒 | +3 | 强兴趣 |
| 收藏 | +5 | 最强兴趣信号 |
| 点击 AI 延伸解读 | +2 | 主动探索信号 |

**示例**：用户收藏了一张"科学"类目的卡片 → 科学类目兴趣分 +5。用户深度阅读了一张"历史"类目的卡片（35秒）→ 历史类目兴趣分 +3。

**存储**：`t_user_interest` 表，`type='category'`，`category_id` 指向类目。

#### 二级兴趣（标签维度）

与一级兴趣类似，但累加的是卡片上的标签。一张卡片可能有多个标签，每个标签独立计分。

**示例**：卡片有标签 `["量子", "物理", "冷门"]`，用户收藏了这张卡片 → 标签兴趣分各 +5：量子=5, 物理=5, 冷门=5。

**跨类目效应**：标签兴趣可以跨类目召回内容。例如用户对"量子"标签有兴趣，即使他从未浏览过"数学"类目的内容，只要"数学"类目下的某张卡片有"量子"标签，也会被推荐。

**存储**：`t_user_interest` 表，`type='tag'`，`tag_name` 存储标签文本。

#### 兴趣衰减

兴趣分不会永远保持，每天凌晨 03:00 自动衰减 5%（乘以 0.95）。

**衰减效果**：
- 7 天不互动：兴趣分剩余 70%
- 14 天不互动：兴趣分剩余 49%
- 30 天不互动：兴趣分剩余 22%

**清理规则**：兴趣分 ≤ 0.01 的记录自动删除，避免低分记录干扰推荐。

**意义**：确保推荐结果反映用户当前兴趣，而非历史兴趣。用户从"喜欢科学"转变为"喜欢历史"时，科学类目的兴趣分自然衰减，历史类目的兴趣分逐步上升。

#### 兴趣分如何影响推荐

推荐时，服务端获取用户 Top 5 类目兴趣和 Top 10 标签兴趣，用于：
1. **候选召回**：从用户感兴趣的类目和标签下召回候选卡片
2. **兴趣打分**：每张候选卡片根据其类目和标签与用户兴趣的匹配程度计算兴趣分

```
卡片兴趣分 = 类目兴趣分 + Σ(标签兴趣分 × 0.5)
```

标签兴趣权重为 0.5（低于类目），因为标签是更细粒度的特征。

### 9.3 内容画像计算

内容画像描述每张知识卡片的质量和热度，用于推荐排序和优胜劣汰。

#### 热度指标（实时更新）

每当用户产生行为，对应卡片的热度指标实时更新：

| 指标 | 更新时机 | 存储字段 |
|------|----------|----------|
| 浏览量 | 用户浏览卡片时 | `t_knowledge.view_count` |
| 收藏量 | 用户收藏/取消收藏时 | `t_knowledge.favorite_count` |
| AI 解读量 | 用户点击 AI 延伸解读时 | `t_knowledge.ai_extend_count` |

这些指标直接参与热度分计算，是内容"受欢迎程度"的实时反映。

#### 质量分（定时计算）

质量分反映内容的用户反馈质量，由定时任务每天凌晨 03:30 批量计算。

**公式**：
```
质量分 = (收藏数 ÷ 浏览数) × [recommend_quality_favorite_rate_weight]
       + (AI解读数 ÷ 浏览数) × [recommend_quality_ai_extend_rate_weight]
```

**计算规则**：
- 浏览量 < [recommend_quality_min_views] 的内容不计算质量分（保持为 0），视为"待评估"
- 浏览量 ≥ [recommend_quality_min_views] 的内容按公式计算

**示例**：

| 卡片 | 浏览量 | 收藏 | AI解读 | 收藏率 | AI解读率 | 质量分 | 等级 |
|------|--------|------|--------|--------|----------|--------|------|
| A | 1000 | 150 | 200 | 15% | 20% | 25 | 优质 |
| B | 500 | 30 | 25 | 6% | 5% | 8.5 | 普通 |
| C | 200 | 3 | 5 | 1.5% | 2.5% | 2.75 | 低质 |
| D | 50 | - | - | - | - | 0 | 待评估 |

#### 优胜劣汰机制

质量分驱动内容的优胜劣汰，体现在推荐排序和运营看板两个层面：

**推荐排序影响**：

| 质量等级 | 质量分范围 | 推荐策略 |
|---------|-----------|----------|
| 优质 | ≥ 15 | 优先推荐，获得更多曝光 |
| 普通 | 5 - 15 | 正常推荐 |
| 低质 | < 5 | 降权推荐，曝光减少 |
| 待评估 | 浏览量 < 100 | 进入新内容池，享受 1.5 倍曝光加成 |

**运营看板预警**：

后台管理的 Dashboard 会自动识别以下问题内容并预警：
- 收藏率 < 3% 的内容（用户不认为值得保存）
- AI 解读率 < 5% 的内容（用户不感兴趣深入探索）
- 纠错率 > 10% 的内容（内容质量可能有问题）

运营人员可根据预警决定是否下架或修改内容。

**内容生命周期**：

```
新发布（0 ~ [recommend_new_content_days] 天）
  │  浏览量 < [recommend_quality_min_views]，质量分未计算
  │  享受 [recommend_new_content_boost] 倍时间衰减加成
  │  进入新内容池优先推荐
  ▼
成长期（[new_content_days+1] ~ [recommend_mid_content_days] 天）
  │  质量分开始计算
  │  优质内容获得更多曝光
  │  低质内容逐步降权
  ▼
成熟期（[mid_content_days+1] 天+）
  │  质量分稳定
  │  进入经典内容池
  │  作为相似内容推荐的种子
```

### 9.4 推荐生成流程

每次用户请求推荐列表时，服务端执行以下流程：

```
用户请求推荐
      │
      ▼
┌─────────────────────────────┐
│  判断用户状态                │
│  - 未登录 → 热门推荐         │
│  - 已登录无兴趣 → 热门推荐   │
│  - 已登录有兴趣 → 个性化推荐 │
└────────────┬────────────────┘
             │
    ┌────────┴────────┐
    ▼                 ▼
 热门推荐          个性化推荐
    │                 │
    │                 ▼
    │          ┌─────────────────┐
    │          │ 候选集召回       │
    │          │ - 类目召回(top5) │  从用户感兴趣的类目下召回
    │          │ - 标签召回(top10)│  从含用户感兴趣标签的卡片召回
    │          │ - 候选池150条    │
    │          └────────┬────────┘
    │                   │
    ▼                   ▼
┌─────────────────────────────────┐
│  去重过滤                        │
│  - 排除 recommend_logs 中        │
│    最近 N 天已推荐的卡片         │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  打分排序                        │
│                                 │
│  热门推荐：                      │
│    SQL 热度分 × 时间衰减         │
│    × 随机扰动                    │
│    [配置:recommend_random_weight]│
│    [配置:recommend_hot_*_weight] │
│                                 │
│  个性化推荐：                    │
│    兴趣分 × [配置:content_weight]│
│    + 热度分 × [配置:hot_weight]  │
│    + 新鲜度分 × [配置:new_weight]│
│    + 随机分 × [配置:random_wt]   │
│    + 运营卡片权重                │
│      × [配置:weight_multiplier]  │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  轻度随机化 + 多样性控制         │
│  - shuffle 范围由配置控制        │
│  - 同类目连续上限由配置控制      │
│  避免每次推荐完全相同            │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  记录推荐日志                    │
│  写入 MongoDB recommend_logs     │
│  用于去重和效果分析              │
└────────────┬────────────────────┘
             │
             ▼
       返回推荐结果
```

**热门推荐的随机扰动**：热度分在 SQL 层乘以随机因子 `(1 - rw + random() × rw × 2)`，其中 `rw` 为 `recommend_random_weight` 配置值（默认 0.1）。当 rw=0.1 时，扰动范围 ±10%，确保每次请求的结果顺序有变化。

**个性化推荐的随机化**：打分排序后，对 top 结果做轻度 Fisher-Yates shuffle（±2 位），避免第一名永远是同一条卡片。

#### 个性化推荐各分项计算逻辑

**① 兴趣分**（见 9.2 用户画像计算）

匹配用户的类目兴趣和标签兴趣，分值越高说明内容越符合用户偏好。

**② 热度分**（归一化到 0-1）

基于卡片的互动指标计算，使用 sigmoid 函数归一化：

```
原始热度 = 浏览量
         + 收藏量 × [recommend_hot_favorite_weight]
         + AI解读量 × [recommend_hot_ai_extend_weight]
         + 运营卡片权重 × [recommend_hot_weight_multiplier]
热度分 = 1 / (1 + e^(-原始热度 / [recommend_hot_score_sigmoid_divisor]))
```

| 原始热度 | 热度分 | 含义 |
|---------|--------|------|
| 0 | 0.50 | 无互动数据 |
| 50 | 0.62 | 轻度热度 |
| 100 | 0.73 | 中等热度 |
| 200 | 0.88 | 高热度 |
| 500 | 0.99 | 极高热度 |

**③ 新鲜度分**（0-1）

基于卡片的创建时间计算，越新的内容分数越高：

| 创建时间 | 新鲜度分 | 配置来源 |
|---------|---------|---------|
| ≤ 1 天 | 1.0 | 固定值 |
| 2 ~ [recommend_new_content_days] 天 | [recommend_new_content_boost] | `recommend_new_content_boost` |
| [new_content_days+1] ~ [recommend_mid_content_days] 天 | 0.5 | 固定值 |
| > [recommend_mid_content_days] 天 | [recommend_old_content_penalty] | `recommend_old_content_penalty` |

新鲜度分确保新发布的内容有机会被看到，避免老内容长期占据推荐位。

**④ 随机分**（0-1）

`Math.random()` 生成的随机数，为推荐结果引入不确定性，防止信息茧房。

**⑤ 运营权重分**

由后台运营人员配置的卡片权重（-2 到 2）乘以 `[recommend_weight_multiplier]`（默认 10），直接加到最终得分中。这是运营干预推荐结果的主要手段。

#### 混合推荐公式（含系统配置标注）

```
最终得分 = 兴趣分 × [recommend_content_weight]
         + 热度分 × [recommend_hot_weight]
         + 新鲜度分 × [recommend_new_weight]
         + 随机分 × [recommend_random_weight]
         + 运营卡片权重 × [recommend_weight_multiplier]
```

其中 `[recommend_xxx]` 表示该值来自 `t_system_config` 表的对应配置项，由后台管理端调节。

#### 热门推荐公式（含系统配置标注）

```
SQL 热度分 = (浏览量
           + 收藏量 × [recommend_hot_favorite_weight]
           + AI解读量 × [recommend_hot_ai_extend_weight]
           + 运营卡片权重 × [recommend_hot_weight_multiplier])
           × 时间衰减系数（由 [recommend_new_content_days/boost/mid_content_days/old_content_penalty] 控制）
           × (1 - [recommend_random_weight] + random() × [recommend_random_weight] × 2)
```

#### 混合推荐公式示例

假设系统配置为默认值，用户对"科学"类目兴趣分=8，某张科学类卡片（运营权重=1）的各分项如下：

| 分项 | 原始值 | 配置权重 | 加权分 | 配置来源 |
|------|--------|---------|--------|---------|
| 兴趣分 | 8.0 | × 0.4 | 3.20 | `recommend_content_weight` |
| 热度分 | 0.73 | × 0.3 | 0.22 | `recommend_hot_weight` |
| 新鲜度分 | 0.8 | × 0.2 | 0.16 | `recommend_new_weight` |
| 随机分 | 0.6 | × 0.1 | 0.06 | `recommend_random_weight` |
| 运营权重 | 1 | × 10 | 10.00 | `recommend_weight_multiplier` |
| **最终得分** | | | **13.64** | |

**调参示例**：如果运营将 `recommend_content_weight` 从 0.4 调整为 0.6，同时将 `recommend_hot_weight` 从 0.3 调整为 0.1：

| 分项 | 原始值 | 新配置权重 | 新加权分 |
|------|--------|-----------|---------|
| 兴趣分 | 8.0 | × 0.6 | 4.80 |
| 热度分 | 0.73 | × 0.1 | 0.07 |
| 新鲜度分 | 0.8 | × 0.2 | 0.16 |
| 随机分 | 0.6 | × 0.1 | 0.06 |
| 运营权重 | 1 | × 10 | 10.00 | `recommend_weight_multiplier` |
| **最终得分** | | | **15.09** |

调整后兴趣分的贡献从 3.20 提升到 4.80，热度分的贡献从 0.22 降低到 0.07，推荐结果更个性化、更不依赖热门。

### 9.5 后台管理参与推荐算法

后台管理端（manage/）通过以下方式参与推荐算法的计算和调控：

#### 9.5.1 卡片权重配置

**操作位置**：知识管理 → 编辑卡片 → 运营权重

**配置值**：-2 到 2 的整数

**对推荐的影响**：

| 权重值 | 最终得分加成 | 效果 |
|--------|-------------|------|
| -2 | -20 | 强降权，几乎不会被推荐 |
| -1 | -10 | 轻度降权，排名靠后 |
| 0 | 0 | 默认，无干预 |
| +1 | +10 | 中等加权，排名靠前 |
| +2 | +20 | 强加权，优先推荐 |

**使用场景**：
- 新上线的优质内容设置 weight=1 或 2，加速曝光
- 被举报或质量差的内容设置 weight=-1 或 -2，减少曝光
- 节日/活动相关内容临时加权

#### 9.5.2 类目权重配置

**操作位置**：类目管理 → 编辑类目 → 运营权重

**配置值**：-2 到 2 的整数

**对推荐的影响**：类目权重不直接参与推荐公式计算，但影响该类目下所有内容的推荐排序。当前实现中类目权重通过 `sort_weight` 字段影响类目列表排序，间接影响用户浏览行为。

#### 9.5.3 系统配置调节

**操作位置**：系统管理 → 系统配置（group=recommend）

**可调节参数**：

| 配置项 | 默认值 | 调节效果 |
|--------|--------|---------|
| recommend_content_weight | 0.4 | 增大 → 推荐更个性化 |
| recommend_hot_weight | 0.3 | 增大 → 热门内容占比更高 |
| recommend_new_weight | 0.2 | 增大 → 新内容曝光更多 |
| recommend_random_weight | 0.1 | 增大 → 推荐更随机、更多样 |
| recommend_dedup_days | 7 | 增大 → 已看内容更久不再推荐 |
| recommend_behavior_dedup_enabled | true | 关闭 → 每次行为都记录（不去重） |

**配置读取与缓存机制**：

```
推荐请求到达
      │
      ▼
┌─────────────────────────────────┐
│  检查内存缓存是否有效            │
│  缓存 TTL = 5 分钟              │
└────────────┬────────────────────┘
             │
      ┌──────┴──────┐
    有效          已过期
      │              │
      ▼              ▼
   直接使用     查询 t_system_config 表
   缓存值       读取 recommend group 配置
                   │
                   ▼
              解析为数值
              解析失败则使用默认值
                   │
                   ▼
              写入内存缓存
              记录缓存时间
                   │
                   ▼
              返回配置值
```

**缓存策略说明**：
- 四个权重配置共享同一个缓存对象，一次性读取
- 缓存键为进程级变量，服务重启后缓存清空，首次请求时重新读取
- 5 分钟 TTL 平衡了实时性和数据库压力：修改后最多 5 分钟生效，每 5 分钟最多查一次数据库

**各配置在计算中的具体参与方式**：

**① recommend_content_weight（兴趣分权重，默认 0.4）**

参与位置：个性化推荐打分公式

```
加权兴趣分 = 兴趣分 × recommend_content_weight
```

- 兴趣分来源：用户对该卡片所属类目的兴趣分 + 标签兴趣分 × 0.5
- 权重越大，推荐结果越"懂你"，但可能陷入信息茧房
- 权重越小，兴趣匹配越弱，推荐越随机

**② recommend_hot_weight（热度分权重，默认 0.3）**

参与位置：个性化推荐打分公式

```
加权热度分 = 热度分 × recommend_hot_weight
```

- 热度分来源：`1 / (1 + e^(-(浏览量 + 收藏×5 + AI解读×3 + 权重×10) / 100))`
- 权重越大，大众认可的热门内容占比越高
- 权重越小，个性化内容占比越高

**③ recommend_new_weight（新鲜度分权重，默认 0.2）**

参与位置：个性化推荐打分公式

```
加权新鲜度分 = 新鲜度分 × recommend_new_weight
```

- 新鲜度分来源：基于 `created_at` 距今天的天数
  - ≤ 1 天 → 1.0（刚发布）
  - 2-7 天 → 0.8（新内容）
  - 8-30 天 → 0.5（常规内容）
  - > 30 天 → 0.2（老内容）
- 权重越大，新内容曝光机会越多
- 权重越小，老优质内容占比越高

**④ recommend_random_weight（随机分权重，默认 0.1）**

参与位置：个性化推荐打分公式 + 热门推荐 SQL 随机扰动

个性化推荐中的作用：
```
加权随机分 = Math.random() × recommend_random_weight
```
- 为每张候选卡片生成 0-1 随机数，乘以权重后加到最终得分
- 权重越大，推荐结果越随机，探索性越强

热门推荐中的作用：
```
SQL 热度分 × (1 - rw + random() × rw × 2)
```
- `rw` 即 `recommend_random_weight` 的值
- 当 rw=0.1 时，SQL 层每次查询的热度分会在 ±10% 范围内波动
- 当 rw=0.3 时，波动范围扩大到 ±30%
- 这是热门推荐结果每次不同的根本原因

**⑤ recommend_dedup_days（去重天数，默认 7）**

参与位置：推荐候选集过滤

```
查询 recommend_logs 中该用户最近 N 天的推荐记录
排除已推荐过的卡片 ID
```

- 值越大，用户看到重复内容的间隔越长
- 值越小，优质内容可以更快地再次被推荐
- 配合 `recommend_random_weight` 使用：去重天数长 + 随机权重高 = 高多样性

**⑥ recommend_behavior_dedup_enabled（行为去重开关，默认 true）**

参与位置：行为上报处理

```
用户上报行为 → 检查开关
  │
  ├─ true（开启）→ 查询 recommend_logs
  │   同一用户 + 同一卡片 + 同一行为类型
  │   在 recommend_dedup_days 窗口内是否已记录
  │   ├─ 已记录 → 跳过，返回"行为已记录（去重）"
  │   └─ 未记录 → 正常记录，更新兴趣分
  │
  └─ false（关闭）→ 直接记录，每次都更新兴趣分
```

- 开启时：防止用户反复操作同一卡片导致兴趣分虚高
- 关闭时：每次行为都记录，适用于需要精确统计的场景（如数据分析）
- 关闭后注意：用户快速反复收藏/取消收藏会导致兴趣分剧烈波动

**配置生效机制**：服务端带 5 分钟内存缓存，修改后最多 5 分钟生效，无需重启服务。

**典型调参场景**：

| 业务目标 | 调参策略 | 预期效果 |
|---------|---------|---------|
| 推广新上线内容 | new_weight: 0.2 → 0.4 | 新内容在推荐中占比从 20% 提升到 40% |
| 提升个性化体验 | content_weight: 0.4 → 0.6 | 兴趣匹配度提升，但多样性下降 |
| 增加内容多样性 | random_weight: 0.1 → 0.3 | 推荐更随机，用户接触到更多新类目 |
| 延长去重周期 | dedup_days: 7 → 14 | 同一内容 14 天内不会重复推荐 |
| 精确行为统计 | behavior_dedup_enabled: false | 每次行为都记录，数据更完整 |

### 9.6 定时任务

推荐系统依赖两个定时任务，均通过 Bull 队列调度：

| 任务 | 执行时间 | 频率 | 作用 |
|------|----------|------|------|
| 兴趣衰减 | 每天 03:00 | 每天 1 次 | 所有兴趣分 × 0.95，清理低分记录 |
| 质量分计算 | 每天 03:30 | 每天 1 次 | 批量重新计算所有内容的质量分 |

#### 兴趣衰减任务

**执行内容**：
1. 将所有 `score > [recommend_interest_cleanup_threshold]` 的用户兴趣记录的分数乘以 [recommend_interest_decay_rate]
2. 删除 `score ≤ [recommend_interest_cleanup_threshold]` 的记录

**意义**：
- 防止过时兴趣长期影响推荐（用户兴趣会变化）
- 自动清理无效兴趣记录，保持数据表精简
- 确保推荐结果反映用户当前偏好

#### 质量分计算任务

**执行内容**：
1. 遍历所有未删除的知识卡片
2. 对浏览量 ≥ [recommend_quality_min_views] 的卡片按公式计算质量分
3. 浏览量 < [recommend_quality_min_views] 的卡片质量分保持为 0

**意义**：
- 质量分依赖浏览量、收藏量、AI 解读量三个指标的比值
- 这些指标实时变化，但质量分不需要实时计算（变化幅度小）
- 每天批量计算一次即可满足运营看板和推荐排序的需求
- 避免每次行为上报都触发质量分计算，减少数据库压力

#### 定时任务执行时间选择

选择凌晨 03:00 和 03:30 执行的原因：
- 凌晨是用户活跃度最低的时段，对线上服务影响最小
- 两个任务间隔 30 分钟，避免资源竞争
- 兴趣衰减在前，质量分计算在后，确保质量分计算使用最新的兴趣数据

### 9.7 定时任务可靠性优化

#### 问题：服务器关机期间任务丢失

Bull 队列基于 Redis，定时任务的调度依赖进程运行。如果服务器在任务执行时间关机，任务不会被执行，也不会在重启后自动补执行。

**场景示例**：
- 凌晨 03:00 应执行兴趣衰减任务
- 服务器在 02:50 关机维护
- 03:10 重启完成
- 结果：当天的兴趣衰减任务未执行

#### 解决方案：启动时检测并补执行

在服务启动时（`onModuleInit`），检查定时任务是否在关机期间被遗漏，如果是则立即补执行。

**检测逻辑**：

```
服务启动
    │
    ▼
┌─────────────────────────────────┐
│  查询 recommend_logs            │
│  获取最近一次任务执行时间        │
│  （通过日志记录或专用状态表）    │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  计算距离上次执行的间隔          │
│  - 兴趣衰减：间隔 > 20 小时     │
│  - 质量分计算：间隔 > 20 小时   │
└────────────┬────────────────────┘
             │
        超过阈值？
        ┌────┴────┐
        是        否
        │         │
        ▼         ▼
   立即补执行   跳过
   记录执行时间
```

**实现要点**：
1. 每次定时任务执行完毕后，记录执行时间到数据库（如 `t_system_config` 中新增 `last_interest_decay_at` 和 `last_quality_calc_at` 配置项）
2. 服务启动时读取上次执行时间
3. 如果距上次执行超过 20 小时（正常间隔 24 小时），判定为遗漏，立即触发补执行
4. 补执行完成后更新记录时间

**幂等性保证**：
- 兴趣衰减任务是幂等的：对同一组数据多次执行 `score × 0.95` 只会导致分数略低于预期，不会产生错误数据
- 质量分计算任务是幂等的：每次都是全量覆盖计算，多次执行结果一致
- 因此补执行不会产生副作用，可以安全重复执行

#### 进阶优化方向

| 优化方案 | 说明 | 复杂度 |
|---------|------|--------|
| 启动时补执行 | 服务重启时检测遗漏任务并补执行 | 低 |
| 执行时间记录 | 将任务执行时间持久化到数据库 | 低 |
| 任务状态监控 | Dashboard 展示定时任务最后执行时间和状态 | 中 |
| 分布式锁 | 多实例部署时防止任务重复执行 | 中 |
| 任务补偿队列 | 使用 Redis 延迟队列实现任务补偿 | 高 |
